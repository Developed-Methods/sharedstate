# Experimental v4 migration rehearsal

The v4 module remains behind `experimental-v4`. It is not an approved production replacement yet.
The [upgrade workflow](../upgrade/workflow.md) records the remaining release gates.

## Prepare the application

Implement `ReplicatedState` with serializable commands, results, and state.
Keep `apply` deterministic and bounded. Encode timestamps and generated identifiers in commands.
Use identical state schemas, initial state, and session limits on every voter.
Audit legacy `authority` implementations for dependencies on stale published snapshots.
Migrate those dependencies into ordered application commands.

Persist each client UUID and its next sequence before submission.
Start sequences at one. Allow one outstanding operation per client session.
Retry `OutcomeUnknown` with the same operation and identical serialized command.
Treat `SessionRejected` as a committed session error.
Treat `NotAdmitted` as a definite rejection before the uncertain network path.
Advancing a session discards its previous cached response but never reapplies an older sequence.
Retirement closes the session permanently. Retired identities still consume the configured session capacity.

## Rehearse the cutover

Create a separate environment with three or five voter databases on local storage.
Generate stable node identities independently from transport addresses.
Keep cluster identity and application schema consistent across voters and readers.
Reserve capacity for 20–50 readers with approximately 60 MB of state each.
Budget memory for each live state, its current immutable publication, and retained application snapshots.

Stop legacy admission. Reconcile outstanding work against application records.
Wait for all legacy nodes to agree on the exported state.
Call `migration::export_quiesced` with that state and its application schema.
Preserve the export and untouched legacy storage.

Call `migration::import_quiesced` to verify the export before creating each new voter.
Open each voter with the imported state and a separate empty SQLite database.
Call `bootstrap` exactly once with the explicit initial voter set.
Wait for a committed revision and compare application state across voters.
Start read replicas with their source directory. Wait for the same committed revision.
Switch clients to the receipt API only after the fault and capacity gates pass.

## Rollback

Before accepting new v4 writes, restore the preserved legacy endpoints and export.
After accepting v4 writes, stop admission and reconcile all uncertain operations first.
Export the complete new application state before restoring a legacy deployment.
Reconcile that state with any external effects and application records.
Do not resume writes from the old snapshot after new committed work.
Application exports do not preserve v4 client-session receipts when importing into the legacy API.

## Current restrictions

Do not mix v1 and v2 voters. The v2 handshake rejects incompatible traffic.
The bundled TCP adapter supports IPv4 on trusted networks and does not authenticate peers.
Durable storage uses SQLite WAL with FULL synchronization and exclusive access per voter database.
The session limit is part of the wire contract and cannot change on restart.
Read replicas provide local, potentially stale reads and cannot acknowledge client writes.
Voters and readers resume snapshots from durable contiguous offsets.
The temporary snapshot quota is 256 MiB per database.
Sources retain leased checkpoints for 60 seconds within a 512 MiB archive quota.
Commands and cached results each have a 64 KiB encoded limit.
A replacement voter receives a complete checkpoint before promotion.
Replace lost voter storage under a new identity; never recreate an empty database under an existing voter identity.
Async shutdown waits for owned workers. Dropping a handle requests cancellation without proving cleanup completed.
The workload benchmark stages replica joins and is not a simultaneous-recovery SLO test.
