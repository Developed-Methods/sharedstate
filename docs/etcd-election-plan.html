Narrow redesign proposal · 9 September 2026 · Checkout 5fc00db · Supersedes the storage redesign plans

Use etcd only for leader election

Replace the custom election algorithm with one lease-backed leader record in etcd.

Keep shared state, actions, snapshots, replication, recovery, and local reads in the existing Rust system.

etcd answers one question: which node currently owns leadership for this cluster?

2. One leased record per cluster

/sharedstate/{cluster_id}/{election_incarnation}/leader
    {
        protocol_version,
        node_address,
        process_session_id,
        phase: "preparing" | "ready"
    }
    attached to: lease_id

LeadershipEpoch = (election_incarnation, key.create_revision)

Use a fresh process session ID for each acquisition attempt. An address alone cannot distinguish a restarted node from its predecessor.

Use the key’s full creation revision as the epoch. Updating its readiness phase preserves that epoch.

The incarnation separates restored or replaced etcd clusters. Provision a new incarnation during such maintenance and restart participating applications together.

etcd transactions support atomic comparisons. Lease expiry removes attached keys, which permits another acquisition. etcd transaction and lease API

Acquisition

  1. Start the existing RPC listener and peer synchronization tasks.
  2. Read the owner record using a linearizable read.
  3. If an owner exists, observe it and follow when it becomes ready.
  4. If no owner exists, eligible can_lead nodes request a lease.
  5. Attempt an atomic create-if-absent transaction with the leased record in preparing phase.
  6. If acquisition loses, revoke the unused lease and follow the recorded owner.
  7. If acquisition wins, maintain the lease while completing the promotion checks.
  8. After preparation, conditionally set the same record to ready.
  9. Enter Leading only after confirming ownership, readiness, and current lease validity.
Acquire:
    IF VERSION(leader_key) == 0
    THEN PUT leader_key = my_preparing_record WITH lease
    ELSE GET leader_key

Publish ready:
    IF CREATE(leader_key) == my_epoch
       AND VALUE(leader_key) == my_preparing_record
    THEN PUT leader_key = my_ready_record WITH same_lease

Use jitter between unsuccessful acquisition attempts. No candidate ranking or address-based winner guarantee remains.

If an acquisition response is lost, read the record and verify its session and lease. Never infer ownership from a timeout.

Observation

Every node observes the same owner key, including nodes with can_lead = false. Observers never acquire leases.

After reading at revision R, watch from R + 1. On compaction, repeat the read and restart the watch.

Use periodic bounded linearizable reads to detect a silent watch. Watch delivery alone has no bounded freshness guarantee. etcd guarantees

Register the advertised owner address with existing peer connections. Continue using initial peers for relay discovery and recovery sources.

An unreachable owner is not permission to replace it. Acquisition remains conditional on the key’s absence.

Resignation

Close local authority admission before releasing ownership. Stop the old epoch’s action production and close its active replication feeds.

Then revoke this session’s lease. If cleanup cannot reach etcd, allow the lease to expire.

Never unconditionally delete the leader key during delayed cleanup. A successor may already own it.

4. Lease loss must stop authority

Model local authority as a revocable permit containing the session, epoch, and conservative monotonic deadline.

Derive renewal deadlines conservatively from request timing and returned TTL. Reject delayed responses that cannot establish a usable remaining interval.

Invalidate the permit on lease expiry, ownership mismatch, renewal failure, or an elapsed deadline. Stop applying authoritative actions immediately.

Check the permit at the actual update boundary, including after awaited work. A boolean checked before an await is insufficient.

After an uncertain session, revoke it and acquire a fresh session before leading again. Do not revive an old permit.

Initially request a 15-second lease and renew around every five seconds. Treat these as test values, with conservative demotion before expiry.

Use the server-granted TTL in the implementation. Validate deadline behavior under delayed responses, scheduler stalls, and process suspension.

Reject stale replication epochs

Carry the origin epoch on authoritative stream envelopes and snapshot handshakes. Relays preserve that epoch rather than substituting their own identity.

Accept a stream only for the locally validated ready owner and epoch. Cancel it on ownership changes or expired observation validity.

A higher epoch claimed by a peer is not proof of ownership. Refresh the etcd record before accepting it.

Following by address alone is insufficient: a restarted leader may reuse its address with a different epoch.

Guarantee boundary: etcd serializes ownership of its key. It does not atomically fence writes to this project’s in-memory state.

Deadlines and epoch checks limit stale-leader activity. A replica with stale ownership knowledge can still accept stale traffic until it invalidates that knowledge.

This narrow change does not establish linearizable replication under arbitrary process pauses or partitions. Do not describe a lease as that guarantee.

External irreversible effects require fencing at their destination. Existing state updates remain subject to the project’s replication and recovery semantics.

Promotion still needs state preparation

The existing election considers recovery compatibility when preferring candidates. Replacing that selection with an etcd race changes which replica may win.

Keep a bounded preparation step before publishing ready. Compare available peer recovery details and recover from a compatible source when necessary.

Reuse existing recovery checks and snapshot transfer. Do not introduce new voting, majority counting, or distributed candidate scores.

If known histories conflict, or required recovery cannot complete, relinquish the lease and report blocked promotion.

A newly started empty node must synchronize before becoming eligible. For an entirely new cluster, explicitly designate its initial-state bootstrap node.

After preparation, perform the existing generation bump once for the acquired epoch. Then publish readiness while the permit remains valid.

etcd cannot establish that the winner has every action from the previous leader. Those actions never passed through etcd.

Keep the existing asynchronous replication loss boundary explicit. If no acceptable recovery source exists, require operator recovery rather than silently bootstrapping empty state.

5. Implement as three focused changes

  1. Add the election adapter. Implement the leased owner record, observation, session deadlines, and ownership status.
  2. Integrate ownership. Replace LeaderTask, add epoch-aware replication checks, and retain state preparation and recovery.
  3. Cut over and remove voting. Update configuration, port election tests, and delete obsolete voting and reachability logic.

Use one etcd client library behind the election module. Keep etcd calls out of DeterministicState and per-action processing.

Use a single-node etcd instance for local development. Test production failure behavior against a three-member etcd cluster.

Required verification

  • Simultaneous contenders produce one ready owner for an epoch.
  • Observers never acquire leadership.
  • Lost acquisition responses cannot create an unverified leader.
  • Lease loss stops authority while peer links remain connected.
  • A paused old leader cannot resume using its expired permit.
  • Epoch changes invalidate direct and relayed streams, including same-address restarts.
  • Compacted or silently stalled owner watches recover correctly.
  • A lagging candidate recovers before readiness; an empty candidate cannot bypass bootstrap rules.
  • Existing action replication, recovery, relay, and TCP failover scenarios continue to pass.

Update tests that expect the lowest node address to win. Assert one observed owner and working replication instead.

Deployment

Provision etcd endpoints, a cluster-specific election prefix, and scoped credentials. Point every participant at the same election configuration.

Pause producers and stop all old election tasks before enabling the new protocol. Preserve node state through the existing recovery mechanism.

Start the chosen prepared node first, then synchronize followers. Resume producers after one ready owner and converged participating replicas are observed.

Do not run legacy voting and etcd ownership simultaneously in one logical cluster. They can authorize different leaders.

Rollback requires stopping all etcd-controlled participants before restarting the legacy election path. Preserve current state using existing recovery procedures.

No shared-state migration into etcd is required. This deployment changes the authority mechanism and its wire metadata.

6. Completion criteria

The custom voting algorithm is gone. etcd determines the owner, and lease validity controls local authority.

The existing state API, local read path, action replication, relay support, snapshots, and recovery remain in use.

The implementation contains no application snapshots, action log, or per-action writes in etcd.

Based on the inspected leader, state-sync, RPC, protocol, discovery, and service modules. This is a plan; no project code was changed.
