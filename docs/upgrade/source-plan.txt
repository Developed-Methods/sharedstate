Recommended direction: durable consensus for writers, committed replication for readers, and explicit ownership of every background task.
Keep fast local reads and support for many replicas. Replace the custom voter election and authority stream with a durable, majority-committed log.
Make leader changes, retries, operation outcomes, and recovery positions visible through typed state and structured events. Remove shared mutable authority from the public API.
1. Design decision and scope
The review found failures in election liveness, delivery, recovery deadlines, reader isolation, shutdown, and framing. Timer fixes alone cannot establish quorum safety.
Use Openraft as the proposed consensus engine. Validate and pin a compatible release during PR02 before building the adapters. Keep its types behind a small internal boundary.
Openraft documents separate log-storage and state-machine interfaces. Its getting-started guide includes learner addition and membership management. These fit the proposed integration boundaries.
Openraft integration guide
.
This plan deliberately strengthens successful-write semantics. A disconnected minority may serve stale reads, but it cannot acknowledge committed writes. Durable state introduces disk and majority-network costs.
If partition-local writes must remain successful, this architecture needs a different conflict-resolution contract. Arbitrary deterministic actions cannot be merged safely without application-specific rules.
Working assumption
Planned behavior
Deployment
Start with three or five durable voters. Add many non-voting read replicas through committed distribution feeds.
Failures
Handle crash/restart, lost connections, delays, partitions, repeated messages, and recoverable disk errors. Peers are trusted; Byzantine consensus is outside scope.
Read policy
Default reads remain local and may be stale. Expose revision and freshness metadata with every snapshot.
Write policy
A successful write means consensus commitment and leader application. Waiting for a particular read replica is a separate operation.
Compatibility
Ship protocol v2 and a major crate version. Keep a small legacy state adapter where its semantics are compatible.
One-minute objective
Measure recovery after a stable majority and adequate resource capacity become available. Include live replicas that have a functioning route.
Persistence
Provide a supported durable voter backend. Limit memory-only storage to explicit tests or disposable development clusters.

Consensus voters and read replicas
Use engine-managed learners for nodes being promoted to voters. Keep ordinary high-fanout read replicas outside voting membership.
Only voters determine commitment. Ordinary replicas consume committed prefixes from voters or trusted relays. Their connection counts and health reports never affect elections.

4. Election, health, routing, and cancellation
Leadership and membership
Persist a random stable
NodeId
independently from network addresses. Persist a
ClusterId
at explicit bootstrap.
Allow bootstrap only against empty storage with an explicit initial voter set. Reject automatic self-bootstrap when seeds cannot be reached.
Delegate elections, vote persistence, log freshness, and membership transitions to the engine. Do not layer custom address tie-breaks onto its decisions.
Add replacements as learners, catch them up, then promote through committed membership changes. Remove retired members explicitly after the transition.
Change addresses without inventing voter identities. Refuse duplicate active NodeIds and mismatched ClusterIds.
Use the engine’s leadership metrics to publish a watch value. Treat it as routing information, not permission to bypass consensus commitment.
Application-level health
Replace Connected/NotConnected as the failure model with

Record successful protocol round trips using monotonic time. Include handshake failures, response timeouts, and stalled reads in failure evidence.
Use peer-health evidence for retry and diagnostics. Let the consensus engine own election timeouts and quorum decisions.
Expire indirect reachability reports. Never extend local health merely because another node repeats an old report.
Run consensus RPCs independently from discovery, client writes, snapshots, and read-replica feeds. Reserve concurrency and byte budgets for consensus control traffic.
Use capped jittered retries for seeds and voters. Bound stale directory entries and discovery payloads without removing voters from committed membership.

Include SessionId on every completion. Check it at the state owner before mutation. Cancelled network reads can still complete, so cancellation alone is insufficient.
Retain timer futures outside select loops, or use watches and persistent intervals. Bound per-batch work so a continuous feed cannot starve control events.

Anti-entropy and progress checks
Exchange committed and applied positions every five seconds initially. Socket keepalives alone cannot show that application state is advancing.
Expose a canonical state digest at explicit committed barriers or retained checkpoints. Compare digests only at the same LogId and schema version.
Require canonical snapshot encoding or a deterministic digest hook from applications. Cache checkpoint digests to avoid hashing an entire large state on every heartbeat.
On mismatch, mark the replica unready and request a verified snapshot from a healthy voter. Quarantine a source after repeated verification failures.
A digest mismatch among voting state machines is a critical invariant failure. Stop normal recovery claims and investigate determinism or corruption.
5. Write API, retry semantics, and deterministic application
Make outcomes explicit in a major-version API. Keep naming provisional until the compatibility spike, but preserve these semantics.
submit(Operation { client_id, sequence, command }, deadline)
    -> CommitReceipt { operation_id, revision, result }
    | NotAdmitted { reason }
    | OutcomeUnknown { operation_id }

operation_status(operation_id) -> Committed | PendingOrUnknown | Retired
wait_for_revision(revision, deadline) -> Applied | DeadlineExceeded
read_snapshot() -> SnapshotHandle { revision, freshness, state }
A receipt means the engine committed the operation and the leader applied it. It does not mean every replica has caught up.
Return NotAdmitted only when the operation never entered an uncertain send or log path. Return OutcomeUnknown after ambiguous timeouts or connection loss.
Retry OutcomeUnknown with the same ID. Never create a new ID silently. Cancelling a future stops waiting; it does not revoke a possibly committed operation.
Deduplication contract
Persist the client identity and monotonically increasing sequence at the client. Limit each client session to one outstanding operation initially.
Replicate the highest applied sequence and last response with application state. Include a payload hash to reject ID reuse with different content.
Return the cached result for a duplicate. Reject gaps and older sequences with explicit session errors. Scale throughput with multiple sessions.
Include deduplication state in snapshots and recovery. Apply the command and advance its session state together in deterministic execution.
Bound session count through admission and explicit retirement. Define a retry-retention contract before adding eviction. Never evict silently and reapply an old operation.
Keep ingress queues bounded by count and bytes. Remove silent draining on leadership change. Pending callers receive a receipt or an explicit uncertain outcome.
State-machine API
Introduce a deterministic
ReplicatedState::apply(command) → result
contract. Apply committed commands in order through one state owner.
Capture timestamps, generated IDs, and other nondeterministic choices in the proposed command. Do not perform network calls or external side effects during apply.
Let the library own log revisions. Keep application-specific sequence fields inside application state only when they have domain meaning.
Provide an adapter for the existing stateless authority conversion and deterministic update contract. Require migration for implementations that depend on stale read snapshots.
Business rejection is a deterministic logged result. An unexpected panic is a node health failure. Do not skip a panicking entry and continue.
Do not promise exactly-once external effects. Applications requiring them need a transactional outbox or an equivalent explicit integration.
6. Durable recovery, snapshots, and read isolation
Storage baseline
Start with one supported SQLite-backed log store using local storage and an ordered I/O worker. Evaluate throughput and crash behavior in PR02.
Use WAL mode and FULL synchronization for the durable profile. Verify pragmas after opening. SQLite documents additional WAL synchronization for FULL commits.
SQLite synchronization settings
.
Keep storage local to each node. SQLite WAL relies on same-host shared memory and is unsuitable for this plan’s storage on network filesystems.
SQLite WAL constraints
.
The backend choice is a proposed default, subject to the spike’s measured durability and throughput gates. Do not implement a new custom WAL format.
Persist votes, ordered log entries, committed position, snapshot metadata, and format versions. Validate cluster identity before serving requests.
Serialize vote and log writes. Complete durability callbacks only after durable commit. Surface disk-full and fsync errors as critical storage failures.
Use the chosen engine’s complete storage test suite. Openraft requires consecutive log entries and serialized write I/O.
Openraft storage contract
.
Recover from a durable snapshot plus the retained committed log suffix. Block readiness until replay reaches the durable committed position.
Follow the engine contract for persisted committed positions when application state remains in memory. Verify recovery ordering before acknowledging writes.
Checkpoint state, applied position, membership, and deduplication as one logical snapshot. Do not independently persist an applied index ahead of its state.
Keep snapshot creation and disk I/O outside consensus runtime threads. Use bounded workers and cooperative cancellation between chunks.

Compaction
Retain required suffixes within a byte budget. If a receiver falls behind retained history, restart from a newer snapshot with an explicit reason.
Catch-up
Apply contiguous committed entries after the snapshot base. Release transfer leases after completion, cancellation, or expiry.
Use native engine snapshot metadata and installation semantics for voters and learners. Keep the read-replica transfer adapter aligned with that metadata.
Prove resumability in the selected transport adapter. Do not assume a library’s snapshot API automatically resumes interrupted transfers.
Immutable read publication
Replace manual quiescent handles with immutable snapshots held by Arc. Use a very short lock to clone or swap the Arc initially.
Clone application state into a new publication version outside the pointer lock. Publish committed batches on a configurable maximum-age schedule.
Old readers keep old versions without blocking writers. Slow readers can retain memory; expose retained-version age and memory diagnostics.
Do not use Arc::make_mut as an unmeasured per-operation full-state clone. Benchmark publication frequency, state cloning cost, and structurally shared application states.
Feed subscribers from retained committed history. A slow subscriber receives a catch-up or snapshot-required outcome. Never await its queue from the apply path.
7. Protocol and transport cleanup
Always write the actual serialized frame length, including static-size messages. Reserve explicit frame tags for keepalive and close.
Check outer frame length before allocation. Check every nested collection against count and byte budgets. Reject trailing payload bytes.
Use distinct limits for control RPCs, commands, replication batches, and snapshot chunks. Start with 64 KiB control and 1 MiB batch limits.
Make command size and maximum snapshot size explicit configuration fields. Reject impossible configurations at startup.
Handshake with protocol version, ClusterId, NodeId, role, and capabilities. Reject incompatible wire or state schemas before decoding bulk state.
Bind claimed NodeId to the configured transport identity. Keep authentication responsibilities explicit in SyncIO for trusted deployments.
Give RPCs request IDs, typed responses, and absolute local deadlines. A late response cannot satisfy a different request.
Propagate remaining time budgets across network hops. Never serialize a process-local monotonic Instant as a cross-node deadline.
Cancel reads, writes, queue waits, connect attempts, and handshakes when their owning task stops. Reconnect after partial frame cancellation.
Use separate transport lanes for consensus, client admission, and bulk state. If multiplexed, enforce priorities at byte scheduling.
Replace generic UnexpectedRequest handling with structured protocol errors. Limit repeated error logs and close invalid sessions.
Remove the two-second whole-snapshot write timeout. Preserve bounded no-progress detection and a separate transfer deadline with resumable recovery.
Use monotonic clocks for timeouts and retry ages. Reserve wall-clock timestamps for human diagnostics. Use persisted random identities instead of millisecond hashes.

Stable identities and event schema
Carry ClusterId, NodeId, engine leader identity, LogId, OperationId, SessionId, and SnapshotId through their relevant paths.
Emit one structured event at each state transition. Include previous state, next state, cause, attempt, elapsed time, and affected revision.

Prevent silent partial service failures
Use reason enums shared by transitions and tests, such as HandshakeTimeout, LeaderChanged, Compacted, Backpressure, and StorageUnavailable.
Log transition summaries at info, detailed batches at debug, and repeated failures with rate limits. Keep operation IDs out of metric labels.
Metrics and inspection API
Expose election duration, leader changes, commit latency, replay throughput, and local applied/committed positions.
Expose RPC deadline failures by stage, retry delay, queue bytes, rejected admissions, and stale-session event counts.
Expose snapshot throughput, restarts, resumptions, digest failures, and publication age.
Expose active tasks by role, child cancellations, shutdown duration, and critical task failures.
Return a coherent NodeStatus containing readiness, leadership, membership revision, publication revision, health reason, and replication state.
Generate a bounded diagnostic event buffer for the last transitions. Export it with failing test seeds and state digests.
Supervision
Own all child tasks in a supervisor with cancellation tokens and join handles. Accepted sockets and transport workers belong to the same tree.
On shutdown, reject new admissions, notify uncertain waiters, cancel transfers, close sockets, flush required storage, and await owned tasks.
Bound graceful shutdown and report tasks that exceed it. Drop triggers best-effort cancellation; only async shutdown promises completed cleanup.
On a critical task panic or storage failure, mark the node unhealthy and stop successful admissions. Rejoin through durable recovery rather than restarting blindly.
Arbitrary blocking application code cannot be forcibly cancelled safely inside Tokio. Document bounded apply behavior and use process isolation if applications need stronger containment.

Measure recovery from the end of the last injected fault, once the supported majority and routes are stable. Do not restart the stopwatch for retries.

Start voter/seed retries at 250 ms, with jitter and a five-second cap. Do not include that cap inside a new unlimited retry deadline.
Set follower publication maximum age initially to 100 ms. Validate this against state size and cloning cost before making it a default.
Specify a supported deployment envelope: voter count, replica count, state size, command rate, RTT, durable-write latency, and available transfer bandwidth.

Retain ordinary RPC and write deadlines separately from the recovery SLO. User-request timeouts should not silently extend until cluster recovery finishes.

Test infrastructure
Extend SimulatedNet with directed links, per-message-class drops, delay, loss, duplication, and bounded bandwidth. Preserve failing seeds.
Inject Clock and random-source interfaces for deterministic scheduling. Avoid SystemTime in protocol decisions.
Record operations and their outcomes in a reference model. Compare counters and ordered effects, rather than only final key presence.
Create a committed barrier after healing. Compare state digests at that exact revision, or pause submissions while collecting equality checks.
Run actual process kills and local TCP tests for persistence and socket cleanup. Tokio task cancellation alone does not model process death.
Use storage failpoints at vote commit, log flush, committed-position persistence, snapshot fsync, manifest update, and compaction.
Run a short deterministic matrix on each PR and expanded randomized schedules nightly. Add a real-time suite using shipped defaults.
Publish workload size, node count, RTT, bandwidth, durable-write latency, and clone cost with every performance result.
Measure leader agreement and state catch-up separately. A single green convergence check does not establish sustained stability under load.
Version the supported envelope with the release. Tests outside that envelope should still preserve safety and return explicit overload or unavailability.
13. Migration, release, and rollback
Treat this as a new wire and storage format. A rolling upgrade that mixes the old custom quorum rules with new consensus would be unsafe.
Build the new cluster in a separate environment. Validate identity, durable storage, snapshots, and fault recovery.
Stop admitting legacy writes. Resolve outstanding operations using application records; the old API cannot prove every queued write completed.
Wait for the legacy cluster to agree on a chosen state. Export it with a schema version and content digest.
Initialize the new cluster once from that snapshot and its explicit voter configuration. Treat it as the new committed base.
Add read replicas and wait for their imported-base revision. Compare digests before sending application traffic.
Switch clients to the receipt-based API. Monitor commit latency, replica lag, task health, and recovery events.
Retain the legacy export and an untouched pre-cutover backup until the new service passes the observation window.
Before accepting new v4 writes, rollback can restore the old endpoints and preserved export. After v4 accepts writes, rollback requires quiescing and exporting the new state.
Never reopen the old snapshot for writes after new committed work without reconciliation. That would discard acknowledged operations.
If the application has an external authoritative replay log, use it to validate the imported baseline. Do not infer historical delivery from legacy enqueue acknowledgements.

All ten findings map to passing desired-behavior regressions. No temporary ignored defect test remains.
Upstream engine storage tests and local crash-recovery tests pass against the shipped backend.
No public reliable API returns plain success for queue admission. All uncertain results preserve operation identity.
Fault tests using production defaults meet the 60-second envelope. Report maximum as well as percentile times.
Pinned readers, slow subscribers, and bounded overload do not stall consensus or other replicas.
Protocol migration, full shutdown, and pre/post-cutover rollback procedures are exercised.
Operational documentation states the quorum-loss, storage-loss, stale-read, and retry-retention behavior precisely.
